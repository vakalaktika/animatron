# Host adapter: ChatGPT (Chat and Work)

Read with `../../SKILL.md`. This adapter only says how the core runs in ChatGPT; the style rules live in the core.

- **Raster illustrations and photo edits:** generate/edit with the available image-generation tool and follow its current schema and image-generation instructions. Supply the selected treatment's style images with the content images (Original: the historical pair; Detailed: the primary scene, plus the adult face crops when adults appear). Use viewed local paths where supported; otherwise use the supported recent-conversation mechanism. Never combine both mechanisms. Recover unavailable bundled assets through supported plugin access before asking the user for that specific input.
- **Host workflows:** when a host such as Storymaker offers its own style-example or approval tools (for example `get_style_examples`), follow `style-presets.md` "Reference authority": parent-authored rules first, then this plugin's written treatment and visual anchors.
- **Native SVG, rigs and motion:** author vector geometry and Rig 1 data directly. The Node scripts (`scripts/*.mjs`, `scripts/validate-rig.cjs`) need a code environment with Node; run them where one is available and say plainly when they could not be run. Do not claim a rig, walk, scene or slim step was baked or validated without running it.
- **Animatron:** compositions are written by the separate animatron-composer skill. Its validation and share links download the Animatron studio and its packages; where the sandbox has no network, those steps cannot run, so say so rather than claiming a validated composition.
- Do not claim equivalent tools across Chat and Work, or identical outputs. Do not transplant Claude-only tool names into ChatGPT.
- **Subagents:** use only orchestration actually exposed by the running ChatGPT Work/Codex session. Installing this skill does not enable it; plain Chat or a session without a spawn tool works inline. Current local Codex can delegate after a direct user request or applicable project or skill instructions that explicitly request delegation; ChatGPT Work normally requires a direct request, with proactive delegation available at eligible Ultra settings. Session instructions take precedence. No special command is needed to request delegation; CLI `/subagents` inspects agent threads. For an unambiguous request say: **"For this large Mid-century Ink job, use subagents for independent units where available, choosing the fastest, balanced, or strongest available model per task; keep treatment, final visual review, and approvals with the lead. If subagents are unavailable, work inline and report that."** One illustration or scoped repair still stays inline under the shared skill.
- **Per-task model selection:** inspect the actual spawn interface and its offered model/effort values before assigning anything. In a Codex session exposing `collaboration.spawn_agent`, use its `model` and `reasoning_effort` arguments; configuration files instead call the effort setting `model_reasoning_effort`. When the interface requires `fork_turns: "none"` for explicit overrides, use that fresh context and supply the full task brief, skill paths and actual visual references. Full-history forks inherit the parent settings. Fixed-model built-in roles may override a requested model: choose a general `worker`/`default` role when explicit per-task selection is needed. Do not claim a model assignment the tool rejected or silently inherited.
- **Codex tier examples, subject to the current tool's supported values:** **fastest** = `gpt-6-luna` at `low` for inventories, hashes and deterministic validators; **balanced** = `gpt-6.1-terra` at `medium` (or available `gpt-6-sol`) for independent views, rigs, clips, native SVGs and scoped corrections; **strongest** = available `gpt-6-astra` at `high`, or `gpt-6.1-sol` at `high`/`xhigh`, for difficult construction, diagnosis and independent visual review. Do not pass Claude tier examples (`haiku`, `sonnet`, `opus`) as Codex model names. Other effort levels are usable only when listed by the current model/tool; never assume that every model supports `ultra` or that chat intelligence labels are spawn parameters.
- **Concurrency and ownership:** launch independent units concurrently only within the runtime's actual slot limit. Assign one output file to each view/clip worker; keep shared models, numbers, treatment, references and approval records under lead control. Brief each fresh worker with the shared skill's required inputs, require it to open the actual reference images, and collect files, checks actually run, errors and unverified work. Give rendered output plus treatment references and Workflow step 7 to a separate strongest-tier reviewer that produced none of the artwork. The lead views every final output and confirms reported defects; a reviewer pass is never user approval.

Official host behavior: [OpenAI subagent documentation](https://learn.chatgpt.com/docs/agent-configuration/subagents). Model names, availability and controls remain session-specific; the running tool schema and higher-priority session instructions govern.
